# Apex IERMS UI modernisation — light theme migration across 27 files

The codebase had a fundamental split between dark glass-morphism UI primitives and page-level components already using Tailwind light-theme classes, producing visually incoherent screens. This change resolves it by rewriting all six shared UI primitives (`Button`, `Input`, `Card`, `Badge`, `Modal`, `Layout`) to a light-theme design system, then propagating the updated primitives through all 16 page-level components across admin, teacher, student, and results areas.

The approach is correct: fix the root at the primitive layer first (FEAT-001), then modernise page components in two parallel batches (FEAT-002, FEAT-003), then apply cross-FEAT integration fixes. All 27 changed files compile cleanly — `npm run lint` exits 0, `npm run build` succeeds at 371 kB.

**Watch for:** No blocking concerns remain. The implementation is complete and all acceptance criteria verified.

**Verdict**: APPROVED

## High-level view

The design token swap in `index.css` is complete — `--bg-app`, `--surface-card`, `--border-default`, `--text-heading`, `--text-body`, and `--text-muted` are all set to the specified light-theme values. Dark utility classes (`.glass`, `.glass-card`, `.btn-*`, `.input-dark`, `.table-dark`) are removed; layout helpers (`.page-container`, `.form-grid-2`, `.form-grid-3`) are added. The `body` rule uses `background-color: var(--bg-app)` with no gradient blobs.

The `Input` primitive correctly handles the `helper` prop TypeScript gotcha — `helper` is destructured out before `...props` spreads to the native `<input>`, so no attribute leaks through. The `Card` primitive drops `glass-card` class usage and makes `glow` a no-op (keeping the prop in the interface for backward compatibility). All six primitives now use white backgrounds and slate-border aesthetics.

Every modal that previously used a custom `<div className="fixed inset-0 …">` overlay has been migrated to the `<Modal>` primitive: AcademicMaster Add Subject, AuditLogsViewer detail view, QuestionBank create form, ExamBuilder build form, MarkEntryGrid add assessment, and ResultsPublication unlock modal. The only intentional exception is `ReportCardModal`, which retains its custom full-width overlay for printable layout — documented in the plan.

Page-level structural requirements all land: AcademicMaster has a four-tab bar switching content; PeopleManager has a search input filtering both student and teacher tables with alternating row striping; ExamDeliveryRoom's header bar is now white/light (not `bg-slate-900`); ReportCardModal academic standing footer is `bg-indigo-700`; ResultsPublication outcome column uses semantic `Badge` variants.
